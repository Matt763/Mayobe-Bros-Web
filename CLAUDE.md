# Mayobe Bros: static site (instructions for Claude)

Plain HTML/CSS/JS site for https://mayobebros.com, hosted free on GitHub Pages. Posts are Markdown files. A
dependency-free Node script (`scripts/build.mjs`) turns them into the HTML pages that get committed and served.
Comments and reactions use a small Cloudflare Worker (`worker/`). There is no other backend.

Node may not be on PATH. If `node` is missing: `export PATH=$HOME/tools/node/bin:$PATH`.

## Publishing a post (the main job)

Read `docs/writing-guide.md` first. It is short and it is the quality bar: simple English, nothing invented,
facts verified against official sources, honest about what could not be confirmed. The site applies to Google
AdSense, so thin, copied, scaled or misleading content can get the whole site rejected.

1. Pick the topic. Do not repeat an existing post (check `content/posts/`). Research it with WebSearch/WebFetch and open every source you cite.
2. Write `content/posts/<slug>.md` (the slug is lowercase words and hyphens, and becomes the URL) with the front matter below, then the body: 1,200 to 2,200 words, `##` sections, short paragraphs, a "Common questions" section, "What to do next", and "Sources and further reading" with real links.
3. Save any image in `assets/posts/` (WebP, about 1400 px wide, under 250 KB), look at it, and write a literal `imageAlt`.
4. Run `node scripts/build.mjs`. Errors stop the build and say what to fix. Warnings (reading level, AI-sounding phrases, missing sources or alt text, income promises, process notes) must be fixed too, unless you can justify one. The build also draws the post's **link-preview picture** (`assets/share/post-<slug>.jpg`, see "Link previews" below): look at it with the Read tool, and if the subject is cut off add `imageFocus:` to the front matter and rebuild.
5. Check the page: `node scripts/serve.mjs` and open http://127.0.0.1:8000/.
6. **Only when the user asks to publish:** first refresh the Popular order with `node scripts/popular-sync.mjs` (it contacts our own Worker; skip it if the Worker cannot be reached, the saved order stays), then rebuild plain with `node scripts/build.mjs` (no `--api` or `--newsletter` flags; a plain build keeps `newsletter/` while `newsletterAction` is `"api"`). Then run `git status` and look for stray files: an empty `css/Mayobe AI` file (the owner's, leave it alone but do not commit it) must not go in (the `newsletter/` folder is now a normal published page). Add files by name, or review the list before using `git add -A`. Then `git commit -m "Publish: <title>" && git push`. It goes live within a minute or two. Never push without being asked.

```
---
title: Clear, specific title (under 70 characters)
date: YYYY-MM-DD
updated: YYYY-MM-DD        # only when you change a published post in a meaningful way
author: Mclean Mbaga       # must match an author in site.config.json
category: educational      # required; see content/categories.json
label: study-tips          # optional; must belong to that category
excerpt: 120-160 characters saying what the reader will learn. No hype.
image: assets/posts/<file>.webp
imageAlt: Literal description of the picture
imageFocus: 40             # optional, 0 to 100: how far down the cover the link-preview picture looks (0 top, 100 bottom)
emailImage: assets/img/topics/<file>.webp   # only when the cover cannot be used in email (e.g. it shows real logos); emailImageAlt: describes it
tags: [three, to, five]
featured: false            # true = on the home page's "Editor's picks"; also first on /popular/ until enough reads have been counted (see "Popular posts")
aliases: [old-slug]        # only after renaming a post, so the old URL still works
draft: false               # true = not published
---
```

All categories and labels are shown, even before they have a post (`"showEmptyTopics": true` in `site.config.json`). An empty one sits under
"More" in the menu (or inline on very wide screens), its page says there are no articles yet and lists the latest posts, and it is `noindex` and
left out of the sitemap until its first post (then nothing needs changing). Label pages with fewer than 3 posts are also `noindex` and not in the
sitemap (thin pages). **Before applying to AdSense set `"showEmptyTopics": false`, rebuild and push**: Google's AdSense checks flag unfinished
or "coming soon" pages, and it is one line to turn them back on later.
To add a category or label, edit `content/categories.json`.
To unpublish a post, delete the file or set `draft: true`, then rebuild.

## Videos in a post
Every video on the site is played by Plyr (files in `vendor/plyr/`, loaded only on pages that have a video). Put one line on its
own in the post body:

```
::video[Caption that says what the video shows](assets/video/clip.mp4){poster=assets/posts/clip.webp captions=assets/video/clip.vtt}
::youtube[Caption](https://youtu.be/VIDEOID){poster=assets/posts/clip.webp}
```

Own videos: save them in `assets/video/` (MP4 H.264 or WebM, keep them small; the site is on free hosting) and give captions
(`.vtt`) when people speak. YouTube: the page shows only the poster and a play button; nothing is requested from YouTube until the reader
presses play, and then it uses `youtube-nocookie.com`. Never paste a raw YouTube `<iframe>` (it would load Google code on page load and
break the Cookie Policy). Once a video has been started and the reader scrolls past it, it keeps playing in a small corner window (the mini player, `miniPlayer()` in `js/site.js`, `.video-figure.is-mini` in `css/style.css`) with buttons to move it (drag, or arrow keys; double-click resets), make it smaller or larger, jump back to it and close it (which pauses it), plus a drag corner for the size. It also takes **touch and mouse gestures on the window itself** (one engine on the window, `js/site.js`, search "Gestures on the window itself"): drag from the picture, a quick flick glides to the nearest corner, two-finger pinch resizes (the picture stays under the fingers), double-tap switches small/large (no fullscreen), and a lone tap shows the controls without pausing (the play button does that). Every gesture has a one-tap button alternative (WCAG 2.5.1, 2.5.7): a size toggle (pinch, double-tap) and a "next corner" button (drag); on touch devices the buttons are 44 px, rest out of sight while playing, the +/- buttons, the move button and the resize corner are replaced by those two, and a tap on the picture brings them back. It works for YouTube too (Plyr's poster layer sits above the iframe, so touches reach the window). **Leaving the browser:** own video files get a "Pop out" button (native Picture-in-Picture, which keeps playing outside the browser); Media Session metadata is set on play and Chrome/Edge desktop pop out automatically when the tab is hidden (only for sites the reader allows); Safari and Firefox cannot be asked to, and iPhone does it from native fullscreen then Home. A YouTube embed cannot be popped out by a page, and YouTube's API policy forbids background-player tricks, so do not add any. Position and size are saved under `mayobebros-mini-player` the position and size are remembered in local storage under `mayobebros-mini-player` (listed in the Cookie Policy, keep both in step); this works for own files and YouTube alike and needs nothing per post. Videos need a useful caption, must be ours or properly licensed, and must not carry the article on their own:
the text must still stand without them.

## Security (reviewed 2026-11-08; keep these in place)
- **Content-Security-Policy:** every normal page and the two email-link pages carry a CSP `<meta>` written by `withPolicy()` / `contentSecurityPolicy()` in `scripts/lib/render.mjs` (GitHub Pages cannot send headers). It lists only what the site loads: our files, the comments Worker, and what `site.config.json` switches on (Cloudflare analytics token, Tag Manager id, AdSense only when `adsense.autoAds` is true, Turnstile only with a key, YouTube after play). The inline scripts are allowed by SHA-256 computed at build time. No `unsafe-inline` or `unsafe-eval` for scripts. When you add a third party or switch ads on, change the builder, rebuild, then check in a browser with the console open (load a post, press Accept, play a video): the test only checks the policy's shape. A meta tag cannot enforce `frame-ancestors`, so clickjacking protection needs real headers (Cloudflare in front of the domain). Redirect stubs have no policy.
- **Posts:** `scripts/lib/markdown.mjs` turns `javascript:`, `vbscript:` and `data:` links into `#`, and neutralises raw `script`, `iframe`, `object`, `embed`, `base`, `meta`, `link`, `form`, `svg`, `math`, `style` tags and `on...=` attributes. Use the `::video` / `::youtube` lines for media.
- **Worker:** every per-visitor limit uses the visitor's network (an IPv6 visitor counts per /64, `visitorNet()` in `worker/src/util.js`); the admin token is compared by hash and admin requests are throttled; bodies announcing more than 4x the limit are refused before reading; held-comment alerts (6 a day), question alerts (4 a day) and contact notices (7 a day) have separate room; a pending newsletter address is never overwritten by a later sign-up; the review (Approve / Ignore) links approve only a comment that is still waiting, and Approve needs a press on the page. The review addresses are never suppressed by a bounce or complaint. Tests: `scripts/tests/security.test.mjs`, `review.test.mjs`.
- **Messages:** visitor-facing wording is short and says nothing about internals, rules or whether something already exists (`scripts/tests/messages.test.mjs` fails on "Sorry", "Please", exclamation marks and technical words). Field errors are "Name is required.", "Email looks incorrect." and so on, shown in red.
- **Fields:** no blue ring: a focused field gets a 2px edge in the text colour (see "Fields" in `css/style.css`).
- **Not done, needs the owner:** Turnstile on the sign-up, contact and comment forms (needs a Cloudflare site key); Cloudflare in front of mayobebros.com for real security headers and a rate-limit rule; moving `REVIEW_EMAILS` (a personal address) out of the public `wrangler.jsonc` into a secret.

## Popular posts: the most-read order (added 2026-11-09)
`/popular/` lists the articles readers really open, most read first, in the same card grid as every listing. **No number is ever shown** (no reads, readers, views or visitors); `scripts/tests/popular.test.mjs` fails if one appears. How it works:
- `js/reads.js` (loaded on article pages when the Worker is on) tells the Worker about one engaged read per page view: the article was on screen for 20 s and 40% scrolled (hidden tabs, prerendering and browsers sending Global Privacy Control or Do Not Track are never counted; nothing is stored in the browser). It sends `POST /v1/read {slug, p}` as plain text (no preflight); `p` is 1 when the reader came from `/popular/`, so that page cannot feed itself.
- The Worker (`worker/src/reads.js`, migration `0010_reads.sql`) counts a visitor once per article per UTC day (a salted hash of article + network + the KIND of browser (system and browser family, not the exact string) + day, kept until the day after; daily totals kept 60 days; the cron trigger purges both; nothing is counted if the `HASH_SALT` secret is missing). Bots (`looksLikeBot`), scripts with no real browser name (`looksTooBare`), unknown slugs, other origins, more than 150 reads a day from one network and more than 4 new visitors from one network on one article in a day are ignored; every answer is the same `{ ok: true }`.
- Ranking (`rank()` in `worker/src/reads.js`; research-based, tuned for low traffic): `S = sum over 28 days of min(reads that day, 10) x 0.5^(age/7)`, a read from `/popular/` counts half; an article needs at least 8 reads on at least 3 different days; eligible ones are ordered by `S - sqrt(S)`. Constants are at the top of the file. It is served only to the owner: `GET /v1/admin/popular` (admin token), never publicly.
- `node scripts/popular-sync.mjs` (add `--dry` to look first) asks the Worker and writes **only the order** of slugs to `content/popular.json` (never edit by hand; the numbers are printed in the terminal only). `scripts/lib/popular.mjs` turns it into the page order: the ranked articles first, then editor's picks (`featured`), then the newest. **Until at least 5 articles qualify the file keeps an empty list, the page keeps its old order and its old honest wording ("Editors' picks first, then the latest stories."); the wording "our readers open most come first, then editor's picks and the latest" appears only when the order is real, and says honestly that only the first articles are ranked.** The order changes only when you run the sync and rebuild (so run it before each publish; a scheduled rebuild could automate it).
- The home page's "Editor's picks" section links to `/post/` (all articles), not to `/popular/`.
- Policies: `privacy-policy.html` ("Which articles are read most", and the retention list) and `cookie-policy.html` describe this; change them with the code. Deploy order: apply the migration and deploy the Worker first (`npx wrangler d1 migrations apply mayobe-engage --remote`, then `npx wrangler deploy` in `worker/`, with `NODE_OPTIONS=--dns-result-order=ipv4first`), push the site second; a site that sends reads to a Worker that does not know the route just gets a harmless error.

## Loading skeleton (added 2026-11-09)
On a slow network the page used to stay white until `css/style.css` (165 KB, render-blocking in `<head>`) arrived. Now every page built by `layout()` starts `<body>` with a skeleton (header shapes, dark hero shapes, one shimmer band) and **then** the `<link rel="stylesheet">`: a stylesheet in the body only holds back the content after it, so the skeleton paints while the CSS downloads (checked in Chromium; a browser that does not paint early just behaves as before, and no unstyled content is ever shown). All of it lives in `scripts/lib/skeleton.mjs` (inline CSS, the markup, and one inline ES5 controller script that the builder hashes into the CSP like the theme script). Rules that keep it from ever being a bug:
- A visitor who clicks a link **inside the site** (the referrer is this origin) gets the stylesheet written into `<head>` with `document.write` instead, exactly as before the skeleton existed: the browser keeps showing the old page until the new one is ready and the page-change fade still runs, and no skeleton is shown (without this an uncached stylesheet gave a white flash and lost the fade; checked in Chromium by sampling frames). Only a cold arrival (typed address, search result, another site) gets the skeleton. The `<head>` stylesheet then appears twice, which is harmless.
- The skeleton CSS is `display:none` unless `html.js` (so no JavaScript = no skeleton), `pointer-events:none`, `aria-hidden`, and has no text. It is invisible for the first 150 ms (`sk-on` is added by a timer), so a fast or cached load never shows it, and it fades out (0.35 s, `transition`, only opacity) the moment the stylesheet fires `load` or `error`, or at DOMContentLoaded, window `load` or a bfcache `pageshow`, then the element is removed. A watchdog also checks every 5 s whether the stylesheet is applied (`body` margin is `0px` only with our CSS) and gives up after 90 s, so a slow connection keeps its skeleton instead of a blank page, and a lost event still cannot leave it up. Whatever happens first wins; every exit is idempotent.
- Do not move the stylesheet back into `<head>` (the skeleton would never paint; `scripts/tests/skeleton.test.mjs` fails), do not put the skeleton anywhere but first in `<body>`, never give it text, never animate anything but `transform`/`opacity`, never put a transform on `html` or `body`, and keep `sk-sweep` unique to this file. Heroes are centred on every page except an article's (bottom-left), and the skeleton follows that (`skeletonHtml(left)`). Status pages (`/manage/`, `/newsletter/`) and redirect stubs keep the stylesheet in `<head>` and have no skeleton.
- Look at it by delaying the stylesheet: in Playwright, `page.route('**/css/style.css*', ...)` with a 2.5 s delay, then screenshot at 700 ms. The shapes follow the real first screen (header heights 4.2rem / 4.75rem from 700px / 9.75rem with the menu row from 1280px); if the header or hero layout changes a lot, change the shapes too.

## Pages that email links open (status pages)
`/manage/` (comment manage link, stop reply emails, the team's Approve / Ignore) and `/newsletter/` (confirm, unsubscribe) are `kind: status` pages in `content/pages/`. `statusPage()` in `scripts/lib/render.mjs` builds them bare: a thin green/blue bar, the logo, ONE card with the answer, and one quiet line of links (home, contact, privacy). No header, hero, footer, article list, search, cookie notice or `site.js`; the page follows the device's light or dark setting first and has a theme button at the top right (`js/status-theme.js`, the same `theme` key and rule as `js/site.js`, so a choice made on the site carries over; `scripts/tests/status-theme.test.mjs` keeps the two in step). **Never hard-code a white background or a fixed text colour in the `.page-status` / `.st-*` block**: the site's text variables turn light on a dark device, and a fixed white card once made the title near-invisible there (fixed 2026-11-08; the status block uses `--bg`, `--surface`, `--link` and the `--st-*` variables, and the test fails on a white background). The card is `.st-card` with `data-state` (mail, busy, ok, info, err) set by `js/manage.js` / `js/newsletter.js`; the look is the `.page-status` / `.st-*` block in `css/style.css` (rise-in cascade, drawn check, ripple, spinner; reduced motion shows everything at once). The scripts keep the `form-status st-status` class on the status line (the stylesheet hides it from the screen in ok, info, busy and err states while screen readers still get it) and change the heading on every outcome. Add a new email-link page the same way (`kind: status`, a card with `data-state`). `scripts/tests/pages.test.mjs` fails if one of them gets a header, hero, footer or article list back.

## The sign-up forms (footer and sidebar)
One builder, `newsletterForm(idPrefix, mini)` in `scripts/lib/render.mjs`, makes both: the footer band (`foot`) and the article sidebar's mini version (`rail`, `.nl-mini` inside `.rail-news`, placed after Read next and the reading path, only when the newsletter is on). `js/subscribe.js` wires every `form[data-newsletter]`; ids carry the prefix so a page can hold both (a test fails on a repeated id). The mini version is always stacked (field, then button), uses the page's own light and dark colours, has shorter confirmation sentences, and reserves its confirmation card's height with a typical address so the module never changes size when it flips. On wide screens (64rem and up) the footer band puts the words left and the form right.
The footer version (`js/subscribe.js`, `.nl-*` in `css/style.css`) is a white capsule (icon, email, Subscribe button) on the blue band. `data-state` on the form is idle, sending or sent. "sent" cross-fades a "Check your inbox" card (a drawn green check, the address back to the reader, "Use a different address") over the form in the SAME grid cell, so nothing resizes: the card's HTML holds a placeholder sentence that reserves its height, keep it. Errors are `role="status"` text with an icon and a short nudge; a near-miss of gmail.com, yahoo.com, outlook.com, hotmail.com or icloud.com is offered back once ("Did you mean ...?", pressing Subscribe again sends it as typed). Focus moves to the card heading on success. The answer never says whether an address was already on the list.

## Listen to this article
Every post gets a Listen button next to the share buttons (`js/listen.js`). It reads the title, then every paragraph, heading and list
item, and stops before "Sources and further reading" (so keep that exact heading text for the sources list). It uses the reader's own
browser voices, highlights the sentence being read, auto-scrolls, and skips pictures, tables, code and videos. Nothing to do per post.
Write numbers and units the way people say them (`TSh 600`, `10 km`, `15%` are read correctly; unusual abbreviations are not).

## Results in search engines: posts and school pages as their own results (added 2026-11-16, owner's request)
The owner wants the results posts AND every school (centre) to be **indexed**, each as its own result: a post (`/post/educational/results/necta-csee-results-2025/`, the page with the search bar) and a school page (`/results/csee/s0107/2025/`, made by the Worker). Nothing here can make Google index a page (it decides); the code makes every page worth indexing, easy to find and honest. Research done 2026-11-16 (Google Search Central, Bing, sitemaps.org; notes in the session).
- **School page title (changed 2026-11-17, owner asked for the best way to name the level and the year; research in `~/necta-work/recon/seo/`):** `<Name> Results 2025: Form Four CSEE`, no brand (`yearPage()` in `results-worker/src/render.js`; name from `displayName()` in `names.js`). The words people type come first (the school and "results <year>", the shape of the commonest searches), the level in plain words plus the acronym after them, where a cut costs least. A ladder of shorter forms (`...: Form Four`, then `<Name> CSEE Results 2025`, then `<Name> CSEE 2025`) keeps every title inside 580 px (Arial 20 px, `titleWidth()` and `TITLE_PX` in `util.js`; Google publishes no limit, 580 px is the width it shows on a computer); the name is never shortened. Measured on 5,790 real pages: 0 titles over 580 px (it was 81% over 600 px with the old format), 0 duplicate titles, 0 duplicate descriptions. Two centres of one exam-year with the same name get the centre number after the name. Files are 10,000 addresses at most, per exam-year; `lastmod` is the date the data was checked, never the cache date. **Not every school is listed: a school-year with fewer than 20 who sat (`MIN_SAT`, 59,302 of 593,774 centre-years, 4,063 centres with no indexable year) is noindex and unlisted, on purpose (thin pages harm the section, and a tiny group is a privacy risk); the owner asked for every school with data on 2026-11-17: the count was reported, the rule was kept until the owner says to lower it (needs `MIN_SAT` in `util.js` AND the `thin` set written by `results-registry.mjs`, then re-upload `registry.json`).**

Suggested: `hubs`, then `all` with `RESULTS_INDEX_FROM=2023`, then lower it as the Page indexing report in Search Console looks healthy ("Crawled - currently not indexed" in bulk means Google is not convinced yet: wait, do not add more). Bing: `node scripts/indexnow-results.mjs --dry-run`, then without it once a day (10,000 addresses a wave, state in `.indexnow-results-state.json`). Run it only after the Worker is deployed, the blog pushed and the owner says so.
- **Crawl friendliness:** every page sends an `ETag` built from the page itself (so it changes with the robots rule, title or data) and answers `If-None-Match` with a 304, plus `Last-Modified` (the data's checked date) for information; `If-Modified-Since` is deliberately NOT used (a date alone kept a crawled `noindex` alive after a roll-out in review); `CODE_V` in `results-worker/src/index.js` goes into the cache key: bump it when a title, description or template changes, because pages stay 30 days at the edge; pages are cached 30 days at the edge; the link-preview picture of a school page is its exam-year's cover card (`%%OGIMG%%` in the shell, `assets/share/post-necta-<exam>-results-<year>.jpg`; a test fails if an exam-year has no card). Links: post to A to Z lists (and regions), lists to schools, school to overview, other years, list letter and post. No `SearchAction` (Google retired the sitelinks search box; the search bar page itself is the indexed result).
- **Posts that hold the search:** the heading and front-matter title stay `NECTA CSEE RESULTS 2025 | MAYOBE BROS` (the owner's), but the `<title>`, `og:title` and JSON-LD name of a post WITH data are `Matokeo ya Kidato cha Nne 2025: CSEE Results by School` (`resultsPostTitle()` in `scripts/lib/results-app.mjs`; Swahili level words lead for CSEE, ACSEE, FTNA, PSLE, SFNA because they are searched about 2 to 15 times more than the acronym; QT `NECTA QT Results 2023: Qualifying Test by Centre`; teachers' exams `Matokeo ya Ualimu 2024: DSEE Results by College`); a post without data keeps its own title. See how any of 6,677 centres performed...` (`resultsPostDescription()`, the search is on the page itself). The hero line carries the Swahili phrase. `WebPage` JSON-LD with `datePublished`, `dateModified` (the verified date) and BreadcrumbList, in `posts-sitemap` with `lastmod` = the verified date.

## Pages and pagination
Every listing (all posts, popular, each category and label, each author) shows 15 posts per page (`postsPerPage` in `site.config.json`).
When there are more, a pagination bar appears under the grid with Newer, Older and page numbers (`/post/page/2/`, `/popular/page/2/`,
`/category/<slug>/page/2/`, `/author/<slug>/page/2/`). These pages are built automatically; nothing to do when you publish. Clicking a page number swaps only the cards and the number bar (`js/pager.js`, no page reload). On category and label pages, the label buttons, the menu and the category tiles also switch in place: the words and cards fade out, the hero picture cross-fades, the new content rises in. Without JavaScript all of these are normal links. The search page
shows 15 results at a time with a "Show more results" button.

**How a page change moves** (one shared module, `js/motion.js`, `window.MBMotion`, loaded first on every page; it also drives the 404 "Posts you may be interested in" pager, search "Show more results", home "Show more posts" and "Show more comments"):
- The old cards fade out (0.16 s). On a slow connection they stay, dimmed to half, while the pressed page number pulses; the grid is never blank.
- The page glides to the top of the list with its own eased scroll (`MBMotion.glide`, easeInOutCubic, 0.26 to 0.52 s, landing 16 px under the real bottom of the sticky header). At most 0.8 of a screen is shown moving: the farther part of a long trip is one jump while the cards are hidden. Any wheel, touch, pointer press or key stops the glide where it is. After a long frame (new cards being laid out, a slow phone) the glide goes on from where it was instead of leaping ahead (`MAX_STEP`, 34 ms of motion per frame), and it always ends within twice its duration. "Show more" only glides when the first new item starts in the lower 40% of the screen.
- The new cards rise in one after another (35 ms apart, the 7th and later together), and focus moves to the first new article (or result, or comment) without scrolling; the focus ring shows only after keyboard use. The page change is announced once (the page bar's `.pagination-note`, on the 404 its `[data-nf-pager-status]`).
- Back/Forward do not bounce: `js/pager.js` sets `history.scrollRestoration` to `manual` while it owns the history entries and back to `auto` on `pagehide`, so Back from an article still lands where the reader was. With reduced motion everything is instant (one jump, same focus and announcement).
- Values: `LEAVE_MS` (fade), `GAP` (landing gap), `STAGGER_CAP` and `MAX_STEP` are constants at the top of `js/motion.js`, the duration in `glideDuration()` and the 0.8 screen cap in `planGlide()` right below; the `mo-wait`, `mo-leave`, `mo-enter` keyframes are the "Motion for in-place page changes" block near the end of `css/style.css` (change both together). No storage, cookies or network: the Cookie Policy is not affected.
- Never use native smooth scrolling for these flows (`scrollIntoView({ behavior: 'smooth' })`, `scrollTo({ behavior })`, or `focus()` without `{ preventScroll: true }`): `html { scroll-behavior: smooth }` makes them race across a long page. Use `MBMotion.glide`. No same-document View Transitions here either: they freeze the page while it updates and cannot carry a scroll. `scripts/tests/motion.test.mjs` guards all of this.
- **A search bar that sticks must bring the reader to the new results** (bug found 2026-11-10: scrolled down near the footer, the reader typed in the sticky results search bar; the list got shorter, the browser clamped the page to the footer and nothing took the reader to the results). In `js/results-app.js`, every user-driven change of the list (typing in either search, an A to Z letter, a division button, the tabs, Clear) passes `follow: true` to `updateExam()` / `updateCentre()`, which run `followResults()`: when the top of the results is above the visible area (under the header and the bar) it runs the change and then `MBMotion.glide`s there with `{ covered: true, keepOnKeys: true }` (`keepOnKeys` = typing does not stop the glide; added to `js/motion.js`). The page-shrink and the first step of the glide happen in one task, so nothing is painted in between. Focus stays in the field. Routes, Back and restore never use `follow`. Other inputs reviewed the same day: the contact form moves to a field or the status line with `bring()` (focus with `preventScroll`, then glide only when it is off screen), the comment form uses `centreIn()` (glide, no `behavior: 'smooth'`), the header search list goes back to its first result on every new search; the search page, newsletter forms and the cookie notice need nothing (the field is never sticky, or the answer appears beside it). `scripts/tests/input-follow.test.mjs` guards all of this. A new sticky input must do the same.

Each post ends with a Previous / Next pair of picture cards (older and newer
article, with a thumbnail from their `image:`); the newest and oldest posts get an "All articles" card instead of a blank gap.

## Link previews (WhatsApp, Facebook, X, LinkedIn, Telegram, Slack, iMessage)
What an app shows when someone shares a link comes only from the `og:*` / `twitter:*` tags in `<head>` and the picture they point at. Every post
(also every category, every label and the home page) gets its own **1200 x 630 baseline JPEG under 190 KB** in `assets/share/`, drawn from the cover
by `scripts/tools/share-card.html` in headless Chromium and encoded by ffmpeg (`scripts/lib/share.mjs`, run by every `node scripts/build.mjs`; about a
second per new card, nothing for unchanged ones; hashes are kept in `.share-cards.json`). Do not point `og:image` at the WebP cover: WhatsApp,
Facebook and LinkedIn may not show WebP, and the covers come in different shapes that apps crop differently.
- The card has the cover, a navy shade, a category chip, the logo and the domain. The title is not on it: every app prints the title, description and domain under the picture.
- What WhatsApp prints under the picture (from its developer guide, checked 2026-11-04): `og:title` in bold on at most 2 lines and "without any branding" (so `og:title` is the plain title, never "Title | Mayobe Bros"); `og:description` on 1 to 2 lines, "80 characters will suffice" (about 90 fit on a phone; the rest is cut), so put the key point of the `excerpt:` first; the domain. Picture: absolute URL, under 600 KB, at least 300 px wide, no more than 4:1; the `<head>` tags must be inside the first 300 KB of the page. Our cards stay under 190 KB because older reports of WhatsApp skipping pictures above about 300 KB exist.
- If a post's subject is cut off (a face at the top, a product at the bottom), set `imageFocus:` in its front matter and rebuild; that is the only per-post control.
- Cards are regenerated when the cover, the category name, `imageFocus`, the template, the logo or the host changes. To redraw everything after a design change, delete `.share-cards.json` and rebuild.
- If Chromium or ffmpeg is missing the build only warns and the page falls back to the home card (a JPEG); `scripts/tests/share.test.mjs` fails until each post has its own card. `CHROME_BIN=/path/to/chrome` overrides the browser it looks for.
- `og:image` carries `?v=<hash>`, so an app that caches by address fetches the new card after a redesign. Apps cache previews: WhatsApp documents no cache time and has no refresh tool (not verified against any official source: reports say a link already sent keeps its old card, and a new chat or a link shared with a query string such as `?v=2` fetches a fresh one). Facebook and LinkedIn do have tools (Facebook Sharing Debugger, LinkedIn Post Inspector). Say this to the owner instead of promising that an old share will change.
- Tags per page: `og:site_name`, `og:locale`, `og:type`, `og:title`, `og:description`, `og:url`, `og:image` (+ `secure_url`, `type`, `width`, `height`, `alt`), `twitter:card=summary_large_image` with title, description, image and image alt, and `article:*` on posts. They sit near the top of `<head>` on purpose; keep them there.
- Check with `node --no-warnings --test scripts/tests/share.test.mjs` after a build.

## Table of contents and questions (what search engines can read)
- The post's "In this article" list and the legal pages' "On this page" list are plain HTML written at build time (`tocList()` in `scripts/lib/render.mjs`), never drawn by JavaScript. They link **every `##` and `###` heading** (the `###` questions nested under their `##`), and every heading has an `id`. That is what lets Google offer "jump to" links for a section; Google chooses whether to show them, and no markup can force it. `scripts/tests/pages.test.mjs` fails if a heading is missing from the list. Write each question in "Common questions" as a `###` heading with the answer in the paragraph right under it, so the question text is the heading a person searches for.
- **On phones and tablets (below 1180px) the contents list is a sticky bar** (added 2026-11-09). It sits above the article, sticks under the site header once the reader scrolls to it, shows "In this article" and, under it, the section being read, and stays until the article ends (then it fades out; it comes back on scroll up). Tapping it drops the list over the article as a panel (`position: absolute`, so the text never moves); the panel folds after a choice, a tap outside or Escape. Large screens keep the open card beside the article, unchanged. The CSS is the "Phones and tablets" block after `.toc summary` in `css/style.css`: **every rule there needs `html.js`** (without JavaScript the list stays an open card above the article, as before) and it lives inside `@media (max-width: 1179.98px)`. `js/site.js` does the rest: `--header-real` (the header's real height, the bar sticks `0.5rem` under it; the root `--header-h` is the 158px desktop header), `.is-stuck` / `.is-past` on `.post-toc`, the section name in `[data-toc-now]` (and `.is-current` on the links, now worked out from the scroll position, not an IntersectionObserver, so a page opened halfway down is right at once), and the end-of-file block that folds or opens the `<details>` (`data-ready` tells the CSS it has run). `js/listen.js` counts the stuck bar when it scrolls to the sentence being read. Anchor jumps stay native (headings keep `scroll-margin-top`, which clears the bar). `scripts/tests/toc.test.mjs` guards the markup, the `html.js` scoping and the open/fold behaviour. The legal pages' "On this page" list is not part of this.
- Do not add FAQPage / QAPage JSON-LD: FAQ rich results are limited by Google to government and health sites (2023; some sources say removed in 2026), and QAPage is for pages where visitors write several answers. The visible headings and answers are what get indexed.
- **Reader questions answered in the comments** are loaded by JavaScript, which search engines may not wait for. `node scripts/qa-sync.mjs` saves every approved comment that is a question (a "?" or a question word, English or Swahili) and has a Team reply, plus those Team replies, into `content/qa.json`. ## RSS feed
`feed.xml` is plain RSS 2.0 for feed readers (the W3C validator passes it). Browsers show it as code, and XSLT styling is being removed from Chrome on 2026-11-17,
so people are never sent to it: every visible "RSS feed" or "Follow with RSS" link goes to the page `/rss/` (copy button, what RSS is, how to follow,
latest articles, questions). Only `<link rel="alternate" type="application/rss+xml">` in `<head>` points at the feed, so readers still find it.
`feed.xml` carries a `text/css` stylesheet (`scripts/tools/feed.css`, built to `/feed.css`) so a person who opens it sees a readable page; CSS on XML is still supported.
Do not add XSLT or scripts to the feed. Do not link third-party reader services from the page unless the link format is verified.
**Since 2026-11-16 every item carries only the title, the excerpt and a "Read the full article on Mayobe Bros" link** (owner's request: the full text in the feed was the easiest thing to copy; `scripts/tests/ai-policy.test.mjs` fails if article markup comes back). The `/rss/` page says so.

## CSS pitfalls found the hard way
- Give every `@keyframes` a unique name. A duplicate name silently replaces the first one (a copy of `page-in` once left a `transform` on `<body>`, which pinned
  every `position: fixed` thing, the Listen bar, the cookie notice and the back-to-top button, to the bottom of the whole page instead of the screen).
- `body` and `html` must never keep a `transform`, `filter`, `contain` or `will-change: transform` after load. Check with
  `getComputedStyle(document.body).transform === 'none'`. Not even for a moment: `body.is-leaving` (the old cross-page fade for browsers without
  native view transitions) once had a `translateY`, which threw a bottom-fixed box from 770 px to 8,918 px down during the fade; it is opacity only now,
  and `scripts/tests/motion.test.mjs` fails on any such rule for `html`, `body` or `:root`.
- The page-change states are keyframe **animations** (`mo-in`, `mo-out`, `mo-dim`), not transitions, so they beat the reveal styles without a specificity
  fight; they animate only `opacity` and `transform`. `html.mo-gliding` (present only while a glide runs) sets nothing but `scroll-behavior: auto` and
  `overflow-anchor: none`. Never animate `height` or `min-height` for a page change: it is a layout shift (CLS).
